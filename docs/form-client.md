# Optional form client adapter

The adapter exported by `jsfe/forms` adds presentation and strict named answer reading. It changes no engine step, session format, form worker, validation transition, confirmation or lifecycle. Hosts that do not use it retain their existing helpers and behavior. No new model or AI role is involved.

## Host contract

The host owns the `formClient: 1` capability; `initSession` and `updateActivity` are unchanged. After a normal engine turn, `projectForm(session)` returns a read-only view of the pending collection request, or `null`. For a compact stored session, pass the loaded definitions as `projectForm(session, engine.flowsMenu)`. A host sends `{answer: session.response, form: view, context}` only to capable clients. The ordinary answer remains intact. Return `form: null` at confirmation, completion or a detour so the UI removes the previous card.

The view has `version: 1`, the owning root instance `form`, `language`, and recursive `fields`. A field has `name`, qualified `path`, `kind`, localized `label`, `required`, `sensitive`, `filled`, optional primitive `value`, optional `error`, and safe numeric `constraints`. A field, group or alternatives the conversation is asking for now carries `current: true` (absent on every other), so a client can point at it when a partly answered form is drawn again. Choice fields have `choices: [{key,label}]`. Nested forms have `kind: 'group'` and `fields`; alternatives have `kind: 'alternatives'`, `required`, `exclusive` and `fields`. Alternative member paths remain relative to their actual form; the group does not introduce a submission object.

## Controls

An input may name the control a card draws for it with `form_client` (still `false` to keep it off the card). It changes only presentation: the profile, validator and conversational reading are unchanged, and the card submits a string the profile already reads.

| Declaration | View | Card |
|---|---|---|
| `{control: 'date', min?, max?, timezone?}` | `control: 'date'`; `constraints` `{min, max}` as `YYYY-MM-DD` | a date picker submitting `YYYY-MM-DD` |
| `{control: 'date', range_from: '<input>', ...}` | adds `range_from`: the start's `path` | the end of a range: one calendar fills the start and this end |
| `{control: 'number', min?, max?}` | `control: 'number'`; `constraints` `{min, max}` | a − / + stepper submitting a whole number |
| `{control: 'place', types, regions?, fills?}` | `control: 'place'`; `place` `{types, regions?, fills?}` | a text box with suggestions from the host's place service, submitting the picked place's own name |
| `{control: 'postal', regions?, fills}` | `control: 'postal'`; `postal` `{regions?, fills}` | a text box the host looks up once the code is complete: the card shows the place it names and fills the fields in `fills` |
| `{control: 'combobox'}` | `control: 'combobox'`; `choices` (possibly none yet) | a text box offering the choices, submitting a picked choice's key or the typed text |
| `{control: 'options', options_from}` (pattern, text) | `control: 'options'`; `options` `[{key, label}]` from the form data `options_from` names (possibly none) | ready replies beside the text box (buttons, or a list when there are many); a pick submits its key exactly as typing it would, so voice and text are unchanged |
| `{autofill: '<token>'}` (alone or with a control) | `autofill` | the box's HTML `autocomplete` token, so the browser may fill it from its saved data |

A date's `min` and `max` are whole days from today in `timezone` (an IANA zone, required with either), turned into dates at each projection; write them as `{"$data": "path"}` to share the values the validator reads. With a control, its bounds replace the profile's (which for some kinds are lengths). Checked at definition time: a control on a profile kind other than pattern, text, digits, amount or identifier, on a `pii` input, an unknown key, a bound that is not a whole number, `min` above `max`, an unknown time zone, or a `range_from` that is not another date input of the form (itself not an end) fails. The profile must still read the submitted shape (`YYYY-MM-DD`, or digits). A place's `types` is `'cities'` or `'address'`; `regions` (optional) lists up to 15 two-letter country codes, projected lower case. The card shows and submits only the place's own name ("7438 Studebaker Rd", "Orlando"), never parts the form has no field for. A place control needs a pattern or text profile, which reads the picked text like a typed one.

`fills` (place and postal) maps other inputs of the form to the part of the place each takes, projected by `path`: a place's parts are `postal_code`, `locality`, `admin_area` and `country`; a postal code's are `locality` and `admin_area`, and a combobox it fills with `locality` also gets the code's other localities as options. A client fills only the fields the card draws, and a value a pick or lookup filled is still the caller's to edit and is read by its own profile on submission. A combobox needs a choice profile with `accept_other` (without the control such a choice is never drawn, since a select cannot hold other text); its typed text is kept, with a letter when the profile asks for `other_needs_letter`. `autofill` is one of a positive list of HTML tokens (names, organization, email, tel, address lines and levels, postal code, country, bday, sex, language, url); never a payment or one-time-code token, and never on a sensitive field. Checked at definition time: `fills` naming the input itself, an unknown or undrawable input or an unknown part, a postal control without `fills`, a combobox on a choice without `accept_other`, or an unknown autofill token fails.

The system address form (`collect-geocoded-address` 1.1.0) uses them on a card only; voice and text keep asking the ZIP code first and derive the city. The ZIP code is a postal lookup filling the city, the street suggests addresses and a pick fills the ZIP code and city, the city (drawn once the ZIP code is known) is a combobox offering the code's place names, and each field carries its autofill token.

## Choice buttons

`projectChoices(session)` returns the options of the question asked now when it has a closed, labelled set, for a client that draws them as buttons or a list: `{version: 1, language, options: [{key, label, say}]}`, else `null`. How they are drawn is the client's choice (the iAIg widget: up to 4 as buttons, more as a list). Only an `ask-choice` question qualifies (a confirmation's YES / NO, a menu, a choice asked in chat), with 2 to 12 options that each have a label in the session's language (`label`, `label_es`; `yes` and `no` have standard ones). Options keyed `event:` are interrupt words and never offered. A tap sends `say` as the caller's own message, read by the question's own reader: the label when the option's words include it, else its first word that is not a number, else its first key. A host offers choices only when no card is drawn (`projectForm` is `null`).

`offeredReplies(session)` returns the words the question waiting now offers as its answers (every choice's phrases and labels, after any runtime trimming), or `[]` when none is pending, on every channel. A host that answers some messages itself before the engine, such as a request to hear the last reply again, checks a message against these first, so an offered answer (AGAIN, OTRA VEZ) always reaches the flow. Since jsfe 1.57.0.

A place control needs a host suggestion service: jsfe calls none and holds no key. The host answers only for a field of the form open now: `formPlaceField(projectForm(session), form, path)` returns the field's `place`, or `null` for any other form, path or control, so the endpoint never becomes a general place lookup. A client without the control draws its ordinary box.

Projection reads resolved presets, linked schemas, existing child instances/results and prepared choice data. It does not open child instances or run preparation/tools. Inapplicable, bound and confirmation fields are omitted (an `internal` input is a question the caller answers when asked, never filled by extraction, so it is drawn); dynamic choices without prepared data wait for the ordinary flow. A sensitive field exposes presence (`filled`) but never its accepted value. `error` carries a worded refusal only; the engine's bare `invalid` flag is not projected. Field questions and unsupported shapes continue to work conversationally; while the field being asked for is one the view omits (`form_client: false`, unprepared choices), `projectForm` returns `null`, so no card stands beside a question it cannot answer.

## Strict prompt convention

```text
JSFE_FORM_V1:{"form":"opaque-instance","values":{"amount":"50.00","card":{"card_number":"…"}}}
```

All leaves are strings. Enumeration values are canonical keys. Omitted/empty values leave existing accepted data intact; there is no explicit clear operation. A `declinable` input (its field carries `declinable: true`, and `declined: true` once answered with no value) may be left blank: the card lists its path in `declined` (`{"form":…,"values":{…},"declined":["unit"]}`), which answers it with no value. Only a declinable field may be named there, and never one with text; a declined field counts as a submitted value. The submission names the actual root instance, not a flow definition. Protocol versions, envelope properties, field paths, nesting and size are checked by `parseFormSubmission(prompt, projectForm(session))` **before** engine execution. A protocol error leaves the saved session untouched. Unknown enum/invalid field values enter normal field validation and produce field errors.

For a successfully preflighted submission, install `formSubmissionReaders(submission, () => engine.getSessionContext())` over the host's `readFormAnswer` and `enrichFormMatches` approved functions for that turn, and restore them in `finally`. These overrides handle only the exact preflighted prompt. They reuse `formInitialReadings`, field profiles and the installed `collect-input-accept` worker; they never write accepted values or approval evidence. Explicit named answers bypass conversational extraction while keeping validators, dependencies, callbacks and proposals. A field sent back with the value the form already holds is not an answer: it is neither acknowledged nor validated again (a card re-sends every field it shows); a changed value is a correction. A submission that changes nothing keeps all its readings. Other answers delegate to the ordinary helpers.

Keep the raw envelope out of language preprocessing, Guru requests and chat logs. The host can use a fixed activity marker by setting the same marker as the preflighted submission’s `prompt` in the readers and as the engine activity content. The local mock performs no AI calls or external business actions. The widget submits through POST `/ask`, and normal conversation can continue through `/askStream`.

## Scope

The adapter preserves existing reentry, partial acceptance, corrections and confirmation. It adds no submission receipts, view revisions, cross-save deduplication or new effect guarantees. A host must still serialize its turns and retain the engine's action/recovery guarantees. Browser drafts are in memory; sensitive edits are not retained across view replacement, and no editable form view is restored from chat history.
